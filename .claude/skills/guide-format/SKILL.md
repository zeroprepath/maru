# guide-format

원본: `/Users/junic/Documents/workspace/projects/maru-journal/guide/Phase0/M0-01.md` ~ `M0-10.md`, `guide/Phase1/M1-01.md` ~ `M1-07.md`, `guide/Phase2/M2-01.md` ~ `M2-04.md`가 이 양식으로 재편된 실제 예시다(2026-09-16, `Build-Phase0.md`·`Build-Phase1.md`는 각각 이 태스크 파일들을 가리키는 인덱스로 남는다 — 「문서 최상위 골격」 참고. 태스크 파일은 같은 날, 사람이 훑어보기 쉽도록 `guide/Phase0/`·`guide/Phase1/` 하위 폴더로 다시 옮겨졌다).

**이 문서의 독자는 사람이다.** "무엇을 구현해야 하는가"의 명세가 아니라 "왜 이렇게 결정했는가"를 설명한다. `tutorial/M1-XX.md`([[tutorial-format]])가 "어떻게"를 맡으므로, 여기서는 실행 가능한 완성 코드·단계별 명령·트러블슈팅 표를 싣지 않는다. 코드가 필요하면 개념을 보여주는 짧은 스니펫만 쓴다(그대로 복붙해서 돌릴 수 있는 완성본이 아니어야 한다 — 완성본은 tutorial 몫).

## 문서 최상위 골격

Phase 문서 도입부(태스크 절 이전)는 다음만 담는다 — 전부 유지:

- 이 Phase가 프로젝트에서 갖는 무게 (왜 이 순서인가, 무엇과 트레이드오프하는가)
- Phase가 끝나면 도달하는 상태 (관찰 가능한 한 문장)
- 이 Phase가 해소하는 리스크와 해소 시점 표
- 겹치는 경력 대비축이 있으면 표로 요약 (어떤 태스크가 "전환"인지)

**프로젝트 전체 온보딩**(태스크 번호 읽는 법·난이도 등급·문서 지도·"각 태스크 파일을 읽는 순서" 같은, 특정 Phase에 속하지 않는 내용)은 Phase 문서에 넣지 않는다. `Onboarding.md`로 분리돼 있다(2026-09-16, Build-Phase0.md에서 분리) — 새 Phase 문서를 재편할 때 이 내용이 섞여 있으면 걷어내 `Onboarding.md`에 합친다.

**파일 분할(2026-09-16, Phase0·1에서 검증 완료)**: 태스크 절은 `tutorial/`이 이미 쓰는 평평한(flat) 구조를 그대로 따라 `guide/Phase#/M#-XX.md`로 한 태스크당 한 파일에 둔다(같은 날 두 번째 정리로 `guide/M#-XX.md` → `guide/Phase#/M#-XX.md` Phase별 하위 폴더로 이동됨 — 사람이 Finder/VS Code에서 훑어보기 쉽도록) — `tutorial/M#-XX.md`와는 파일명만 같고 폴더 경로가 달라, "왜"와 "어떻게"가 항상 짝으로 찾아진다. `Build-Phase*.md`는 위 도입부 넷 + 태스크 인덱스 표만 남기는 **인덱스**가 되고, `guide/` 최상위에 그대로 남는다. 버전은 파일명(`.v2` 등)이 아니라 git 커밋이 담당한다.

## 이 문서 시리즈를 고칠 때 지키는 규칙 (2026-09-16 확정, `Build-Phase1.md` 인덱스와 동일)

1. **태스크 파일은 그 태스크가 끝난 시점의 이상적 상태로 쓴다.** "(YYYY-MM-DD 발견)" 같은 사후 발견 날짜, 나중 Phase의 구체적 사건("M1-04에서 버튼이 안 보였다" 같은)을 본문에 남기지 않는다. 새로 드러난 내용은 트레이드오프 항목(기계적 원리 → 선택지 → 결론)이나 기존 결정의 적용 범위를 명확히 하는 문장으로 접어 넣는다. 발견 과정 자체는 `/dig`로 `learning/`에 남긴다.
2. 본문에 볼드로 처음 등장하는 기술 용어는 다음 중 최소 하나를 가져야 한다: `시작 전 필수 개념` 링크 / `Glossary.md` 항목 / `착수 게이트` 질문.
3. `시작 전 필수 개념`에 넣은 항목 수만큼 `착수 게이트` 질문도 1:1로 있어야 한다.
4. 새 트레이드오프 결정은 "기계적 원리 → 선택지가 대신해주는 것 → 결론" 3단을 따른다.
5. 새 Glossary 항목은 "왜 필요한가 → 뭔가 → 다음에 뭐가 문제되는가" 3단을 따른다(`Glossary.md` 참고).
6. **다른 태스크(`M#-XX`)를 본문에서 언급하면, 그 태스크가 이미 파일로 분할되어 있는 한 마크다운 링크로 건다.** 같은 Phase면 `[M1-05](M1-05.md)`(같은 폴더). Phase가 다르면 `../Phase#/`를 붙인다 — `[M0-10](../Phase0/M0-10.md)`(태스크 파일 안에서), 인덱스(`Build-Phase*.md`)에서는 `../` 없이 `[M0-10](Phase0/M0-10.md)`. 아직 파일이 없는 태스크(아직 안 쓰인 Phase 뒤쪽의 `M3-XX`·`M4-XX` 등)는 가리킬 파일이 없으므로 텍스트 그대로 둔다. 자기 자신(예: M1-06 문서 안에서 "M1-06")은 링크하지 않는다.

## 의존 관계

- **선행 조건**: 이 태스크가 시작 전에 이미 있어야 하는 이전 태스크의 산출물 (예: `[M1-01](M1-01.md)(SDP/ICE 수동 교환 경험)`(같은 폴더), `[M0-04](../Phase0/M0-04.md)(ClientToServer 계약)`(다른 Phase))
- **이후 태스크가 참조**: 이 태스크가 만드는 것 중, 아직 쓰이지 않지만 이후 태스크가 그대로 갖다 쓸 개념·타입·계약이 있으면 여기 명시한다. 왜 지금 만드는지 한 문장으로 적는다 (예: "`error.code`에 `NOT_APPROVED`·`INVALID_TOKEN`을 지금 넣어두는 건 [M1-05](M1-05.md)가 채워 넣을 자리를 선취하는 것이다"). **이 필드가 비어 있는 게 기본값이 아니다** — 전방 참조가 있는데 안 적으면 독자가 "왜 지금 이게 나오지?"에서 막힌다.

## 명시적으로 빼는 것

- 실행 가능한 완성 코드 블록 (그대로 복붙하면 동작하는 것)
- 단계별 명령어 나열, 터미널 조작 순서
- 트러블슈팅 표(증상→원인→조치)
- 동작 확인 체크리스트(`두 탭을 열면 영상이 보인다` 같은 것 — 이건 tutorial의 "여기까지 확인"에 흡수된다)
- AI 위임 구역·방어 구역 운영 판단 (`Workflow.md` 소관)

이 다섯 가지가 파일에 남아 있다면 그건 아직 tutorial로 옮기지 않은 기존 콘텐츠다 — 재편 시 들어낸다. (`시작 전 필수 개념`·`착수 게이트`·`TL;DR`은 위 다섯과 다르다 — 이들은 빼는 게 아니라 반드시 있어야 하는 신설 섹션이다.)
